# 静哨 QuietSentry · 技术方案与架构设计

> 对应 MTask：W03 / T03734　依据：[PRD-QuietSentry.md](../PRD-QuietSentry.md) §10（技术实现要点）、第 7 章功能需求
> 基线：已实现 MVP（commit `ce98af9`），构建 `assembleDebug` 通过；本文按"代码已落地部分 + 待落地部分"分开描述，避免设计与实现脱节。

## 1 范围

本文覆盖 PRD §10 的五类技术问题：相机管线、编码与分片容器、事件检测、连接与加密、保活与功耗。

其中 MVP 已实现：相机管线（无预览采集）、前台服务保活、分片录制与断录修复、黑屏拍照。
尚未实现：事件检测、观看端连接与加密、录像索引与保留策略、功耗分级。

## 2 分层架构与代码映射

```text
表现层
  ├─ MainActivity          值守控制 + 预览 + 能力展示
  └─ BlackScreenActivity   黑屏记录（拍照 / 切镜头 / 退出）

领域层（本轮为轻量编排，未独立分层）
  ├─ 模式编排：值守（持续录像） / 黑屏（按需拍照）
  └─ 待补：设备与配对、事件与录制索引、告警与权限

基础设施层
  ├─ CaptureService        LifecycleService：相机绑定 + 分片循环 + 前台通知
  ├─ CameraCapabilities    系统能力探测（镜头、最大录制尺寸）
  └─ 文件系统              应用私有目录 clips/ 与 private_gallery/

平台
  └─ CameraX 1.4.1（camera-core / camera2 / lifecycle / video / view）
```

现有代码规模适合"服务内编排"；当观看端、事件检测接入后，再把编排逻辑抽到领域层（`domain/`），本轮不提前抽象。

## 3 采集管线

| 模式 | 使用用例组合 | 关键约束 | 代码位置 |
| --- | --- | --- | --- |
| 值守（息屏持续录像） | `VideoCapture<Recorder>`（不绑 Preview） | 相机绑定在服务内的自定义 LifecycleOwner，与 Activity 无关 | [CaptureService.kt](../app/src/main/java/com/quietsentry/app/CaptureService.kt) |
| 黑屏（按需拍照） | `ImageCapture`（不绑 Preview） | Activity 生命周期绑定，`FLAG_KEEP_SCREEN_ON` 保持屏幕点亮但不发光 | [BlackScreenActivity.kt](../app/src/main/java/com/quietsentry/app/BlackScreenActivity.kt) |
| 放置与调角度 | `Preview` | 仅用于主界面取景，不参与录制 | [MainActivity.kt](../app/src/main/java/com/quietsentry/app/MainActivity.kt) |

设计理由：

- **不绑 Preview 是"息屏可用"的前提。** Preview 一旦存在，相机会为 Surface 分配额外缓冲与 GPU 合成开销，且部分设备在屏幕关闭时会因预览 surface 失效而中断会话。
- **两种模式不同时绑定相机。** CameraX 的 `unbindAll()` 是进程级相机占用切换点；值守中打开黑屏页会打断录像，因此黑屏记录入口只在值守未运行时可用（待 W09 加互斥提示）。

## 4 息屏值守生命周期

```text
Activity 点击「开始值守」
  └─ startForegroundService(ACTION_START)
       └─ CaptureService.onCreate：建通知渠道 → startForeground(camera[|microphone])
            └─ onStartCommand(ACTION_START)：repairInterruptedClips() → 异步取 ProcessCameraProvider
                 └─ bindToLifecycle(cameraOwner, DEFAULT_BACK_CAMERA, VideoCapture)
                      └─ startNextSegment()（30 秒一片，Finalize 后递归下一片）
```

关键机制：

| 机制 | 做法 | 为什么必须这样 |
| --- | --- | --- |
| 生命周期解耦 | 服务内自建 `LifecycleOwner`，`LifecycleRegistry.currentState = RESUMED` | `LifecycleService` 自身不会进入 RESUMED；若不伪造，CameraX 拒绝打开相机 |
| 前台服务 | `foregroundServiceType="camera\|microphone"` + 常驻通知 | Android 11+ 限制后台使用相机，只有 camera 类型前台服务可继续；通知也是用户可见的采集凭据 |
| 通知常驻 | `setOngoing(true)` + 「停止」动作 | 采集状态必须随时可确认、可停止 |
| 权限降级 | 无录音权限时不申报 microphone 类型、且不 `withAudioEnabled()` | Android 14+ 申报 microphone 类型要求权限已授予，否则 `startForeground` 直接抛异常 |

已知限制：部分厂商 ROM 在锁屏后仍会冻结后台相机；MVP 未申请电池优化豁免与厂商白名单引导（PRD §10.4 列入 W11+）。

## 5 分片录制与断录修复

```text
prepareRecording → 写 .pending（内容=片名）→ start
      ├─ Finalize 正常 → 删除 .pending → 启动下一片
      └─ 进程被杀 → 留下 .pending
启动时 repairInterruptedClips()
      ├─ 片可解码（MediaMetadataRetriever 取到时长）→ 保留
      ├─ 片不可解码（缺 moov）→ 重命名 orphan_*.mp4（保留证据，不删除）
      └─ 删除 .pending 标记
```

设计取舍：

| 决策 | 取值 | 理由 |
| --- | --- | --- |
| 分片时长 | 30 秒 | 越短则进程被杀损失越少；越长则文件数越少、索引越轻。30 秒是两者的折中 |
| 容器 | MP4（边录边写） | 系统相机与播放器兼容性最好；配合 `.pending` 标记可识别未收敛文件 |
| 损坏处理 | 重命名为 `orphan_` | 直接删除会丢掉可能可部分恢复的取证素材 |
| 编码 | CameraX `Recorder` 默认（硬件编码优先） | MVP 不显式选 HEVC，交给系统按设备能力选择；后续按 PRD §10.2 显式 HEVC→H.264 回退 |

当前缺口：分片之间有几毫秒到几百毫秒的间隙（Finalize 回调后重新 prepare），PRD 的"事件前后缓冲"要求连续缓冲，需在 W10+ 改为预分配双缓冲切换。

## 6 权限与前台服务类型矩阵

| 权限 | 用途 | 缺失时行为 |
| --- | --- | --- |
| `CAMERA` | 采集、拍照 | 不允许启动值守（点击时重新请求，失败则提示） |
| `RECORD_AUDIO` | 录像含声音 | 降级为纯画面录制，前台服务不申报 microphone 类型 |
| `POST_NOTIFICATIONS`（Android 13+） | 前台服务通知可见 | 服务仍可运行但通知不可见；PRD §10.5 要求此类情况禁止启动值守，待 W09 收紧 |
| `FOREGROUND_SERVICE` / `_CAMERA` / `_MICROPHONE` | 前台服务类型申报 | 清单缺失会导致启动即崩溃 |

## 7 线程模型

| 工作 | 线程 | 说明 |
| --- | --- | --- |
| CameraX 绑定与录制启动 | 主线程（`ContextCompat.getMainExecutor`） | CameraX 要求在具备 Looper 的线程上调用 |
| 分片文件写入 | CameraX 内部线程 | 由 `FileOutputOptions` 驱动，不占主线程 |
| 断录修复校验 | 服务主线程（当前实现） | 遗留分片很多时会阻塞；后续移到 `Dispatchers.IO` |
| 拍照回调 | 主线程 | 只更新界面状态 |

## 8 存储布局

```text
/data/data/com.quietsentry.app/
├─ files/
│  ├─ clips/
│  │  ├─ clip_YYYYMMDD_HHMMSS_N.mp4
│  │  ├─ clip_....mp4.pending
│  │  └─ orphan_clip_....mp4
│  └─ private_gallery/
│     └─ pic_YYYYMMDD_HHMMSS.jpg
```

- 全部位于应用私有目录，不进入系统相册、不被媒体扫描器索引（PRD §10.3 本地数据策略）。
- 保留与循环覆盖已实现（`StorageKeeper`，W09）：先清理 7 天以上的文件，再把总量压到「当前可用空间的 50%」以内；两种删除都跳过最近 24 小时的文件——正在录制的分片 `lastModified` 持续刷新，删掉会在用户无感知的情况下中断录像。
- 检查时机：值守启动时一次、录制过程中每 10 个分片一次、黑屏拍照成功后由后台线程一次。每片都扫描目录不划算，间隔太长又可能在一轮长时间录制里写满存储。
- 尚未实现：删除回收站（最近删除保留 7 天）。当前没有用户删除入口，待事件回看页（W13）一并补齐。

## 9 能力探测与降级

`CameraCapabilities.describe()` 读取 `CameraManager.cameraIdList` 的 `LENS_FACING` 与 `SCALER_STREAM_CONFIGURATION_MAP.getOutputSizes(MediaRecorder)`，输出"镜头 id · 朝向 · 最大录制分辨率"。

- 为什么不用固定配置：旧设备镜头组合与录制尺寸差异极大，后续画质档位必须按探测结果动态置灰，否则用户选了不支持的分辨率会直接启动失败。
- 当前仅用于界面展示；W09 起作为画质选项的数据源。

降级矩阵沿用 PRD §10.5，其中与本轮实现直接相关的两条：

| 能力 | 最低要求 | 降级 |
| --- | --- | --- |
| 无预览后台采集 | CameraX 可用、Android 9+ | 回退 Camera2；仍不可用则仅保留黑屏模式 |
| 持续通知 | Android 13+ 通知权限 | 无权限不允许启动值守（待收紧） |

## 12 验证口径

编译级：`gradle assembleDebug` 通过（AGP 8.7.3 / JDK 17 / Gradle 8.9 / SDK 35）。

端到端（需真机，当前阻塞）：

1. 值守开始 → 按电源键熄屏 5 分钟 → 唤醒停止，检查 `clips/` 是否连续分片、首尾是否可播放。
2. 值守中 `adb shell am force-stop` 强杀 → 重启应用，检查 `.pending` 是否被清理、坏片是否变成 `orphan_`。
3. 黑屏页单击 5 次 → 检查 `private_gallery/` 生成 5 张可解码 JPG；双击切换镜头后再次拍照成功。
4. 拒绝录音权限后启动值守 → 服务不崩溃、生成无音轨视频。

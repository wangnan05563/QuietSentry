## 1 本轮已落地的降级路径

W23 把"能力探测"从展示升级为**运行时决策**：镜头选哪颗、录多大、打不开怎么办，全部由设备真实能力决定。

| 场景 | 旧行为 | 现行为 | 代码位置 |
| --- | --- | --- | --- |
| 设备无后置镜头 | 直接绑 `DEFAULT_BACK_CAMERA`，启动抛异常 | 按 后置 → 前置 → 任意镜头 顺序选主镜头；用前置时通知写明"本机无后置镜头" | `CameraCapabilities.primary()` / `selector()` |
| 录制尺寸不支持 1080p | 固定默认档位，准备录制即失败 | `Quality.FHD → HD → SD` 有序回退，探测不到 1080p 就不申请 FHD | `CameraCapabilities.recorder()` |
| 外接 / 朝向未知镜头 | 绑到内置后置，画面不符预期 | 按朝向精确匹配（`requireLensFacing`），不再落回默认后置 | `CameraCapabilities.selector()` |
| 相机被其他应用占用 | 只在 catch 里报错并停掉，用户以为设备坏了 | 注册 `AvailabilityCallback`：占用时通知"等待释放"，释放后自动重绑；绑定失败再重试 3 次 / 3 秒 | `CaptureService.watchCamera()` / `retryBind()` |
| 重绑时的旧分片 | 无处理，`Finalize` 会续写落在旧 capture 上 | `rebinding` 标记阻断自动续片，由重绑成功后统一起新片 | `CaptureService.bindCamera()` |
| 相机彻底不可用 | 通知停在"采集中"，语义错误 | 明确"本机没有可用相机，可改用黑屏记录"并清掉值守标记 | `CaptureService.bindCamera()` |

**未实现且不承诺：** Camera2 手工回退管线（PRD §10.5 提到的"回退 Camera2"）。代价是重写一套采集/录制/编码，风险高于收益；当前用"CameraX + 有限重试 + 明确失败提示"覆盖，Camera2 回退降级为 P1 候选，见 §5 风险。

## 2 最低版本与 API 分支

| Android 版本 | API | 本产品的差异化处理 | 验证点 |
| --- | --- | --- | --- |
| 9 Pie | 28 | 最低支持版本；通知渠道、前台服务均可用 | 值守启动、熄屏采集、分片修复 |
| 10 | 29 | 首次出现 `foregroundServiceType` 参数 | 申报 camera 类型后 `startForeground` 不抛异常 |
| 11 | 30 | 分区存储强制 | 私有目录读写、相册导出（MediaStore） |
| 12 | 31 | 前台服务启动限制收紧 | 从通知/界面启动值守成功，后台启动被拒有提示 |
| 13 | 33 | `POST_NOTIFICATIONS` 运行时权限 | 拒绝通知权限时不允许启动值守 |
| 14 | 34 | camera 类型前台服务不可从后台/开机广播创建；申报 microphone 需已授权 | 拒绝录音权限时退化为纯 camera 类型且不崩溃；`BootReceiver` 只提示不启相机 |
| 15/16 | 35+ | 后台限制继续收紧 | 同 34，另验证前台服务超时提示 |

依赖的具体分支：`CaptureService.startForegroundWithType()`（API 29+ 类型参数、录音权限判定）、`Diagnostics.notification()`（API 33+ 权限）、`MainActivity.beginGuard()`（API 31+ 后台启动限制）。

## 4 七天稳定性测试清单

连续 7×24 值守，每天只做一类注入，结束后检查当日全部分片可解码、索引与事件可回看。任一天出现"通知显示值守中但观看端无画面"即整体不通过（静默失效是本产品最不可接受的失败形态）。

| 天 | 注入 | 步骤 | 通过判定 |
| --- | --- | --- | --- |
| D1 | 基线 | 接电源、常亮熄屏值守 24h，每小时记录电量/温度/心跳 | 分片连续无缺口；温度 ≤45°C 或触发降载而非停采；心跳间隔 ≤90s |
| D2 | 断电 ×3 | 每次值守中直接拔电源/长按关机，重启后打开应用 | 每次最多损失 1 个进行中的分片；启动时 `.pending` 被清理、坏片改名 `orphan_`；不自动拉起相机而是提示恢复 |
| D3 | 强杀 ×5 | `adb shell am force-stop`，间隔 ≥30 分钟，第 3 次后不打开应用 | 第 3 次起出现"反复被中断"建议；返回应用后一键恢复；历史分片全部可播放 |
| D4 | 网络抖动 ×10 | 关 Wi-Fi / 切飞行 / 切换热点，各 10 次 | 本地录制不中断；恢复后离线摘要只推 1 条，不刷屏 |
| D5 | 热与充电 | 边充边录 + 覆盖散热差的放置，持续 8h | 45°C 触发降载文案；50°C 暂停并说明原因；不出现"默默停止" |
| D6 | 存储压力 | 预填存储至可用 <1GB，值守 4h | 按 7 天保留 + 50% 配额清理；始终保留最近 24h；录制不因清理中断 |
| D7 | 重启 ×5 + 总检 | 每次重启后走恢复流程，最后全量回看 | `BootReceiver` 只发"设备已重启"提示，不启动相机；全部分片可解码；无 ANR/崩溃 |

**长时间观测指标（PRD §12 量化口径的落地值）：**

| 指标 | 目标 | 采集方式 |
| --- | --- | --- |
| 文件可打开率 | ≥ 99%（不含撞上写入瞬间的那一片） | 逐片 `MediaMetadataRetriever` 校验，失败数 / 总片数 |
| 分片时长偏差 | 30s ± 3s | 读取每片 `METADATA_KEY_DURATION` |
| 心跳间隔 | ≤ 90s（超过即观看端标记"疑似中断"） | `DeviceHttp.Status.heartbeatAt` 与服务端 `serverTime` 差 |
| 恢复提示时延 | 重启后 ≤ 1 分钟出现 | 通知出现时间戳 |
| 崩溃 / ANR | 0 | `adb logcat` 全量过滤 `FATAL`/`ANR` |

## 5 风险与未覆盖项

| 项 | 影响 | 处置 |
| --- | --- | --- |
| 无 Camera2 回退 | 极少数 CameraX 初始化失败机型无法值守 | 明确失败提示 + 引导黑屏模式；列为 P1 |
| 只支持 ≤480p 录制的设备 | `QualitySelector` 可能协商失败 | 归入"相机彻底不可用"分支并提示；矩阵中单独记录 |
| 厂商 ROM 杀后台 | 采集中断 | 依赖 W22 心跳/被杀检测/白名单引导；D3/D7 专门覆盖 |
| 真机不可用 | 本矩阵仍为待执行 | 与 T03774（模拟器环境修复）合并，先模拟器跑通再逐品牌真机 |

## 6 判定口径

- **PASS**：§3 六个必测项全部符合预期，且无"通知与实际不一致"的静默失效。
- **FAIL**：出现以下任一即判 FAIL，需附 `adb logcat -b all` 相关片段：值守显示运行但无画面且 10 秒内无提示；强杀后历史分片不可播放；拒绝权限路径崩溃；降级文案缺失。
- **N/A**：设备确实不存在该能力（如无前置镜头），需在备注写明"能力不存在"，不能当作 PASS。

## 1 背景与目标

### 1.1 为什么再做一次梳理

`docs/07`（T03977）在 2026-11-02 交付了一份竞品对标 UI 优化 PRD，其 7 个实施批次在此后的 27 个提交中已基本落地。继续沿用该文档的「差距诊断」会产生两类偏差：

- 把已完成能力当成待办。例如 `docs/07` 把「观看端无扫码能力」列为 P0 缺口，而 `bbfdf9c`（T04045）已新增 `ScanPairActivity.kt`（zxing `QRCodeReader` + CameraX 预览），`a48aade` / `ca3a871` 也已让空态三条配对路径全部可见。
- 把已过时的设计 token 当成现状。`docs/02 §6.1` 仍记「卡片 12dp、正文 14–16sp」，而 `dimens.xml` 在 `0b30402`（T04060）后已是卡片 20dp、正文 15sp。

因此本轮重新以**当前代码**为基线：先确认哪些体验问题已被解决，再只针对仍存在的缺口定义需求，避免重复排期。

### 1.2 调研目的

1. 从 GitHub 上真实存在、定位相近的开源项目中，提取可迁移到「单 App 双角色、局域网直连、无账号」架构内的 UX / UI 实践。
2. 把竞品优势映射为可评审、可验收的需求条目，每条都标注现状证据与验收口径。
3. 收口设计系统一致性问题，为后续所有界面改动提供单一视觉来源。

### 1.3 预期达成的体验指标

| 指标 | 目标值 | 测量方式 | 当前状态 |
| --- | --- | --- | --- |
| 首屏到开始值守的点击数 | ≤ 2 次（权限已授予时） | 冷启动后人工计数 | 主按钮随状态切换已落地（`db0b032`），**待实测** |
| 值守状态可核对性 | 3 秒内可说出「是否在录 / 已运行多久 / 剩余空间」 | 5 名未用过本产品的人观察首页 | 状态卡 10 秒轮询已落地（`831e462`），**待实测** |

### 1.4 范围边界

- **只覆盖**：用户体验流程、界面布局、视觉规范、组件规范、动效，以及与之直接相关的性能 / 兼容性 / 可访问性约束。
- **不覆盖**：检测算法与模型重构、服务端与网络架构变更、账号 / 云 / 订阅 / 远程中继、多语言翻译、新增系统权限（扫码复用现有 `CAMERA` 权限）。
- **事实口径**：竞品特性只写仓库主页与 README 可核实的内容；由特性推导出的界面评价统一标注为「设计判断」，不冒充竞品公开事实；不引用未核实的下载量、星标数等易变数据。

## 2 竞品分析报告

### 2.1 选取与核实方法

从主 PRD §2.2 记录的 14 个同类开源项目中，按「体验代表性」选取 5 个，覆盖录制、局域网推流、端侧 AI 告警、多机位四种形态。2026-11-08 逐个访问 GitHub 仓库主页并读取 raw README 核实存在性与特性，记录见附录 A。

**事实修正**：`docs/07 §2.1` 中的 `https://github.com/Tea-n-Tech/android-ip-camera` 返回 HTTP 404；真实仓库为 `https://github.com/DigitallyRefined/android-ip-camera`（与主 PRD §2.2 一致）。本文件及后续引用一律使用已核实链接，该错误链接已在本轮同步修正。

### 2.2 五个竞品逐项对比

#### 2.2.1 FadCam — 后台录制器

- **仓库**：[anonfaded/FadCam](https://github.com/anonfaded/FadCam)
- **已核实特性**：README 自述为「隐私优先的 Android 多媒体套件」，包含后台视频录制、行车记录、屏幕录制、直播与远程控制，无广告且开源；主 PRD §2.2 另记录其定制 Media3 分片 MP4（边录边写）、进程被杀后自动检测并修复、Web UI 远程控制。
- **UX 交互实践**：把「当前是否在录、录了多久」作为首页主对象；对「进程被杀 / 存储满」给出专门的恢复路径，而不是一条通用报错。
- **UI 视觉实践**：Web UI 远程控制在单页内承载状态与操作，信息密度高而不堆叠入口。【设计判断：基于其「live streaming & remote control」功能描述与 Web UI 形态推导，非 README 明文；不引用未经核实的截图细节】
- **差异化优势**：录制文件的抗损坏与恢复能力，是其状态可信度的基础。
- **对静哨的启示**：状态可信度与异常闭环优先于增加功能入口。

#### 2.2.2 LensCast — 局域网 WiFi 相机

- **仓库**：[raulshma/lenscast](https://github.com/raulshma/lenscast)
- **已核实特性**：README 描述为「通过 WiFi 向浏览器推视频 / 音频的 Android 相机应用」，提供专业相机控制、远程 Web 访问、间隔拍摄与定时录制；技术栈徽章为 Kotlin、Jetpack Compose、Material 3、CameraX；README 内嵌 camera / settings / gallery / streaming / controls 五张分页面截图。
- **UX 交互实践**：按任务把界面切成「相机 / 设置 / 图库 / 推流 / 控制」五块，参数按组收敛，而非所有开关平铺。
- **UI 视觉实践**：使用 Material 3 设计系统统一控件形态与色彩。【已核实：README 明确标注 Material 3 与 Jetpack Compose】
- **差异化优势**：相机专业参数与网络质量分级的产品化组织方式。
- **对静哨的启示**：用统一设计系统 + 分组参数控制长设置页的信息密度；这正是 §4.2.3 组件库升级的参照。

#### 2.2.3 android-ip-camera — 极简局域网推流

- **仓库**：[DigitallyRefined/android-ip-camera](https://github.com/DigitallyRefined/android-ip-camera)
- **已核实特性**：README 自述为「Android H.264 / MJPEG IP Camera app」；内建服务器，浏览器打开地址即可看流；支持关屏推流、RTSP 主码流与子码流、ONVIF（WS-Discovery / 快照 / 运动事件）、远程 Web 控制，可接入 Frigate 与 Home Assistant；README 附桌面浏览器截图。
- **UX 交互实践**：把「打开浏览器看到画面」作为最短路径，不需要先理解设备、账号或配对流程。
- **UI 视觉实践**：以画面为主体，控制项收在远程 Web 界面，移动端接近零界面。【设计判断：基于其「Built in server, just open the video stream in a web browser」的 README 表述推导】
- **差异化优势**：协议层完整（RTSP / ONVIF），产品层刻意保持极简。
- **对静哨的启示**：首屏先给画面或明确状态，控制项后置；静哨已通过快照兜底（`bff531c`）朝此方向落地。

#### 2.2.4 Retired-Sentinel — 端侧 AI 安防

- **仓库**：[Feebami/Retired-Sentinel-App](https://github.com/Feebami/Retired-Sentinel-App)
- **已核实特性**：README 自述把闲置 Android 手机变为安防相机，100% 端侧推理（YOLO26 检测、ML Kit 人脸裁剪、FaceNet 身份比对），陌生人触发时把滚动帧编码为 MP4 经 Telegram 推送；提供温控 / 电池保护（分辨率与帧率限制）与从图库录入可信身份；README 附「检测到入侵者 / 可信身份已验证」两张演示动图。
- **UX 交互实践**：告警携带可判断的证据（人 / 非人区分、视频片段），用户不必点开每条事件才知道发生了什么。
- **UI 视觉实践**：用「入侵者 / 安全身份」两态演示图直接说明产品价值。【已核实：README 两张 GIF 及图注】
- **差异化优势**：事件语义（人 / 非人）与证据链，而非单纯的运动帧。
- **对静哨的启示**：事件卡片的信息密度与语义筛选；静哨已有 `EventType.PERSON` 与「有人形」筛选项（`EventTimelineActivity.kt:91/104`），下一步是把它做成可一眼分辨的卡片层级。

#### 2.2.5 HomeSentry — 分布式多机位

- **仓库**：[obrassard/HomeSentry](https://github.com/obrassard/HomeSentry)
- **已核实特性**：README 自述为「把旧手机变成分布式安防摄像头系统」的开源平台；技术栈包含 WebRTC、Angular / TypeScript Web 控制台与移动客户端，为 HackThe6ix 2020 第一名项目。
- **UX 交互实践**：多台设备在 Web 控制台一屏总览，单机位可聚焦查看。【设计判断：基于其「distributed security camera system + Web dashboard」形态推导，README 未逐项描述交互细节】
- **UI 视觉实践**：以多画面网格组织主界面，单画面放大为二级视图。
- **差异化优势**：多机位并发总览，是单个手机 App 视角的天然补充。
- **对静哨的启示**：≥840dp 宽度下的多设备网格仍是静哨空白（见 §3.2 G4），是本轮唯一新增的功能型体验需求。

### 2.3 商业参照（不计入上述 5 个）

AlfredCamera 采用摄像头端 / 观看端双 App 角色与扫码配对，并用 Trust Circle 表达成员共享（来源：主 PRD §2.3）。它不是 GitHub 开源项目，仅用作首次配对流程与文案表达的参照，不参与本文件的功能事实对比。

### 2.4 横向结论

| 体验维度 | 竞品共同做法 | 静哨现状 | 本轮是否立需求 |
| --- | --- | --- | --- |
| 状态可信度 | 录制 / 在线状态常驻且可核对 | 首页状态卡已落地 | 否，仅补实测（UX-04） |
| 信息层级 | 按任务分页面、参数分组、控制后置 | 入口收敛与设置页当前值已落地 | 部分，收敛为统一组件（UI-03） |
| 首屏给画面 | 浏览器 / 应用首屏先给画面 | 首帧快照兜底已落地 | 否 |
| 事件语义 | 人 / 非人区分、告警带证据 | `PERSON` 类型与筛选项已落地 | 否 |
| 多机位总览 | Web 控制台一屏网格 | 未实现 | **是（UX-01）** |
| 设计系统一致性 | Material 3 等单一来源 | 双套色彩令牌 + 布局硬编码 | **是（UI-01 / UI-02）** |

结论：静哨在「功能面」已覆盖竞品的合集，剩余差距集中在**设计系统一致性、多设备总览、以及已交付能力的实测证据**三处，而不是继续堆功能。

## 4 优化需求列表

### 4.1 用户体验（UX）优化：痛点 → 改进方案

| 编号 | 痛点与现状证据 | 改进方案 | 交互细节 | 验收口径 |
| --- | --- | --- | --- | --- |
| UX-01 | 多设备只能逐台进入，缺一屏总览（G4；HomeSentry 对标） | 在 ≥840dp 宽度新增 2×2 多画面网格，单机位可聚焦并返回 | 网格仅展示已有设备的实时画面与状态角标；并发路数不得突破现有服务端观看上限，实施前以 `DeviceServer` / `DeviceRegistry` 实际约束复核；聚焦返回不重建播放器 | 4 台设备同屏可见；点击任一路 2 秒内出画面；折叠 / 展开往返不中断播放 |
| UX-02 | 空态三条配对路径视觉权重相同，用户仍需判断先点哪个（G3） | 明确「扫码」为主按钮，配对码 / 手动 IP 为次按钮；三步说明压缩为一行引导 | 三条路径必须继续全部可见，不得退回「先点添加再选方式」；按钮文案沿用 `strings.xml` 现有条目；主按钮视觉权重高于两个次按钮 | 空态一屏无需滚动；TalkBack 能依次读出三条路径；三条路径均可走通配对 |
| UX-03 | 异常态由首页横幅、实时页弹窗、修复文案各自定义（G5） | 抽出统一「异常态组件」：图标 + 一句原因 + 唯一主动作 + 可选重试 | 覆盖离线、断流、权限缺失、配对失效四类；主动作直达系统设置 / 重新配对 / 重试；组件只承接展示，不改变现有触发逻辑 | 四类异常均出现同一组件且都带下一步动作；不出现无解释的空白页 |
| UX-04 | 已交付能力缺可观测的体验数据（G6） | 为 §1.3 的点击数、定位耗时、断网恢复时长补本地计时日志，写入 `verify-output/`（运行产物，不进版本库） | 只记耗时与结果，不采集画面、设备标识或任何用户信息；日志格式沿用现有验证脚本风格 | 5 项指标各有一条可复核记录；`docs/07 §8` 验收清单可据此逐条勾选 |

### 4.2 UI 升级与美化

#### 4.2.1 色彩规范（UI-01）

- **现状**：`colors.xml` 曾并存 `qs_*`（线上令牌，被全代码引用）与 `qs_color_*`（设计令牌，经检索 0 引用，死令牌）；二者主色与状态色取值均不同（G1）。T04776 / UI-01 已移除 `qs_color_*`、确立 `qs_*` 为唯一来源。
- **需求（已落地）**：以 `qs_*` 单一色彩令牌集为唯一来源，移除死令牌 `qs_color_*`；状态色（`ok / warn / danger / idle`）只用于状态表达，不作为按钮底色；主色取线上值 `qs_accent #FF00BFA6`（青色，值守场景不刺眼），`qs_color_primary #FF0F766E` 备选未采用、留作独立设计决策。结论已同步回写 `colors.xml`（注释）与 `docs/02 §6.1`。
- **约束**：不引入新色系；正文 / 状态文字对比度 ≥ 4.5:1；状态不得只靠颜色区分（沿用 `docs/02 §6.1` 的「图标 + 文字」规则）。

#### 4.2.2 布局调整（UI-02）

- **现状**：多个布局仍有硬编码色值与尺寸（G2）。
- **需求**：所有布局统一引用 `dimens.xml` 现有 token——字号 20 / 24 / 15 / 13 / 12sp，间距 4 / 8 / 12 / 16 / 24dp，卡片圆角 20dp、按钮 10dp；清除 `#99FFFFFF` 一类硬编码色值，改引 `colors.xml`。
- **断点**：沿用 `<600dp` 单列、`600–840dp` 双栏、`≥840dp` 双栏 + 事件侧栏的现有规则（`0b8f54a` 已落地），本轮只在 ≥840dp 增加 UX-01 的网格视图。
- **约束**：系统字号放大到 1.3 倍不截断，沿用 `item_device.xml` 的 `minWidth / minHeight` 实践，避免固定尺寸裁字。

#### 4.2.3 组件库升级（UI-03）

- **现状**：空态用原生 `Button`（G3）、卡片底用 `qs_card_bg.xml`、画质用 `live_quality_pill_item.xml`，同类控件形态分散。
- **需求**：先定义 6 个基础组件的规范与资源，再逐页接入，不一次性重写布局：

| 组件 | 规范要点 | 首接入页面 |
| --- | --- | --- |
| 主按钮 | 填充式、唯一主动作，最小触控 48dp | 设备列表空态（UX-02） |
| 次按钮 | 文字 / 弱填充，不与主按钮竞争 | 设备列表空态（UX-02） |
| 状态卡 | 模式 + 时长 + 余量，10 秒刷新 | 摄像头端首页 |
| 设备卡 | 快照 + 状态角标 + 时间线，选中态不改圆角 | 设备列表 |
| 异常横幅 | 图标 + 原因 + 主动作 + 重试（UX-03） | 首页 / 实时页 / 配对页 |
| 空态容器 | 说明图 + 主次按钮组，一屏不滚动 | 设备列表 / 事件时间轴 |

- **通用规则**：每个组件统一定义 `contentDescription`、按压态、禁用态与 TalkBack 朗读顺序；组件内部不写死中文文案，一律引用 `strings.xml`。

#### 4.2.4 动效设计（UI-04）

- **规范**：只保留两类动效——页面进入 180ms 淡入上移、状态切换 120ms 颜色过渡（沿用 `docs/07 §4.6` 已定数值）。
- **禁止**：循环动画、值守界面持续动效、闪烁提示；页面不可见即停止动画。
- **可访问性**：尊重系统「减少动态效果」设置，开启时直接跳到终态；动效不承载唯一信息，状态变化必须同时有文字。

Product Requirements Document

静哨 QuietSentry

把闲置 Android 手机或平板，变成一台可以息屏值守、本地优先、随时远程查看的家用监控摄像头。参考 QuietCam 的黑屏交互，结合 FadCam、lenscast、android-ip-camera 等开源实现，收敛为一条可交付的产品主线。

版本 v0.9 状态 待评审 日期 2026-10-31 平台 Android 首发 文档类型 常规 PRD（Heavy）
版本提示：本文件为 v0.9 可视化评审稿，仅用于阅读体验与交互演示。Q1–Q8 的决策已回填至 PRD-QuietSentry.md（v1.0），两者冲突时以 Markdown 版为准。

00一页结论

用户不需要再买一台摄像头：家里那台被淘汰的手机，只要能持续拍摄、安静地待在一个角落、并且随时能看到，就已经是一台可用的监控设备。本 PRD 定义的产品，负责把这个"已经存在但没人用起来"的能力，变成一条三分钟内可以走完的完整路径。

产品主张

三分钟，把旧设备变成摄像头

摄像头端生成配对码，观看端扫码即连；不强制注册账号；默认局域网直连，数据不出家门。

核心体验

屏幕可以全黑，采集不能中断

值守模式真正熄屏；黑屏记录模式保留 QuietCam 的"点击即拍"；两者都通过持续前台通知让采集状态可被确认。

商业与合规

本地优先，云端可选

默认不把原始画面交给第三方；云备份、远程中继是显式开启项。明确排除"无通知的隐蔽拍摄"。

三个必须同时成立的判断

判断依据对产品的影响
需求真实存在 Alfred 累计覆盖 7000 万以上家庭；GitHub 上十余个"旧手机变摄像头"项目在 2025–2026 年持续活跃。这说明"用旧设备做监控"不是小众玩法。 不与硬件厂商正面竞争，主打"零硬件成本 + 旧设备复用"。
现有方案是碎片化的 开源项目大多只解决一段：IP 摄像头只做推流，录制类只做落盘，AI 类只做检测，多机位方案还需要自建服务器。商业方案则把回看、多机位、AI 锁进订阅。 产品价值来自"串起来"：配对、值守、告警、回看、恢复在同一条链路里。
平台有硬约束 Android 14 起，camera 类型前台服务不能从后台创建，也不能从开机广播启动；持续通知不可隐藏；部分市场强制快门音。 "静默"只能定义为不亮屏、不显示预览、不播放应用内提示音；不能承诺"无痕"或"开机自动偷拍"。

01背景与目标

1.1 观察到的现象

现象具体表现用户代价
旧设备大量闲置 换机后旧手机、旧平板留在抽屉里，硬件完好、摄像头可用、电池尚可，但没有再用处。 沉没成本；想临时看家时又要买新设备。
商业方案收紧免费额度 AlfredCamera 2026 年免费版限制为最多 2 台在线摄像头，Premium Standard 年费由 29.99 美元上调至 35.99 美元；回看与事件功能对新账号进入付费墙。 "先免费用用看"的路径变窄，用户开始寻找买断或自托管方案。
隐私顾虑阻止使用 多数商业方案默认把画面传到厂商云；部分应用的数据安全标签披露位置等信息的收集。 家庭内部画面不愿上云；对"谁在看"没有可见证据。
开源方案只解决单点 FadCam 解决后台息屏录制与抗损坏文件；lenscast / android-ip-camera 解决局域网流与远程 Web 控制；Retired-Sentinel 解决端侧人形识别；HomeSentry 需要自建服务端。 普通用户要在三四个 App 之间拼装，且缺少统一的设备管理、告警与回看。

1.2 目标用户与关键时刻

目标用户是"有闲置设备、有临时或长期看护需求、但不想新增硬件或订阅"的家庭用户。触发时刻通常很具体：出差前想看门口、白天上班想知道宠物在做什么、老人独居需要有人知道有没有异常、租房期间担心入户。

1.3 产品回应

把三个动作合成一条路径：配对 → 值守 → 回看。摄像头端只做一件事：稳定采集并把事件留在本地；观看端只做一件事：让我随时知道家里发生了什么。所有跨设备的复杂度（发现、连接、加密、重试、补传）由产品吸收，不交给用户。

1.4 可观察的成功标准

  • 新用户从安装到摄像头端进入值守，全程不超过 3 分钟，且不需要阅读帮助文档。
  • 观看端在局域网内能打开实时画面，画面延迟低于 1 秒量级；公网访问有可用路径。
  • 发生运动事件后，用户能在事件列表中看到一段可播放的片段，并且能判断事件发生的时间与位置。
  • 摄像头端被系统杀死、断网、低电、过热时，观看端能收到明确的原因提示，而不是"设备离线"四个字。
  • 在完全不启用云服务的情况下，以上链路仍然成立。

02调研基线

2.1 QuietCam：被点名参考的黑屏交互

QuietCam 是一款同时发布于 iOS 与 Android 的黑屏相机，由独立开发者维护。它解决的不是"监控"，而是"在不点亮屏幕的情况下记录"。对本产品最有价值的不是它的功能清单，而是它验证过的三条交互：屏幕保持黑色时相机仍在工作；点击任意位置即可拍摄；长时间按住可以隐藏界面控件。

能力QuietCam 的做法本产品的取舍
屏幕形态纯黑、锁屏壁纸或自定义图片作为背景，界面无可见预览。保留。作为"黑屏记录模式"，用于临时放置与私密记录。
拍摄方式点击任意处拍照；长按隐藏控件。保留单击拍照、长按隐藏；增加双击切换镜头。
存储本地私有图库，不要求账号，不做分析上报。保留本地优先；但监控场景必须增加事件索引与远程告警。
付费点PRO 解锁 4K 60fps、音频录制、连拍。不作为首发付费点；分辨率与帧率按设备能力开放。
平台差异Android 不提供时间戳叠加；Action Button 为 iPhone 独有。Android 端以"屏幕内水印 + 文件元数据"替代，不承诺硬件快捷键。
定位差异个人私密记录工具，不提供远程观看与值守。本产品在其交互之上叠加"值守 + 远程 + 事件"三段能力。
结论：QuietCam 证明了"黑屏可用"，但没有证明"黑屏可长期值守"。后者需要前台服务、保活、事件检测与远程链路，正是本产品要补的部分。

closecircuit 离线多机位 Wi-Fi Direct 组网；WS-Discovery 发现摄像头；监控端作为热点，多台设备直连，完全不依赖路由器。 场景极窄（车载/婴儿看护），无长期值守能力。
Haven 传感器安防 用运动、声音、震动、光线传感器做入侵监测；通过 Signal / Tor 安全告警；面向记者与人权工作者的威胁模型设计。 不做视频流与画面回看，与本产品是互补而非替代。
OfflineMotionCamera 纯离线相机 不申请 INTERNET 权限，运动触发拍摄，全部留在设备内。 无法远程查看，"离线"是优点也是边界。
IP_Cam 可管理 IP 相机 内置 Web 管理界面、HTTP API、在线检查与更新。 界面与运维方式偏工程化。
VigiLens 静默录制 息屏后台录制、本地存储、隐私优先的设计取向。 功能深度有限，缺少监控链路。
IpCam MJPEG 发射器 CameraX + NanoHTTPD 的最小实现，适合作为协议层参考。 无产品化能力。

2.4 平台与合规约束

这些约束不接受产品愿望，只接受工程事实。它们直接决定哪些承诺可以写进 PRD。

约束具体内容对需求的改写
camera 前台服务类型 Android 14（API 34）起必须声明 camera 服务类型并申请 FOREGROUND_SERVICE_CAMERA，同时持有 CAMERA 运行时权限。 采集必须有前台服务与持续通知；不能仅靠后台线程。
后台启动限制 应用处于后台时不能创建 camera 类型前台服务；也不能从 BOOT_COMPLETED 广播启动该服务。 "关机重启后自动恢复拍摄"不可承诺；改为重启后提醒用户打开应用确认。
持续通知不可隐藏 前台服务必须显示持续通知；Android 13+ 还需要 POST_NOTIFICATIONS 授权。 "静默"限定为不亮屏、不显示预览、不播放应用内提示音；通知必须保留。
系统快门音 部分市场与机型对快门声有强制策略，第三方应用无法绕过。 能力清单中标注"受系统策略限制"，不作为卖点。
厂商后台管理 国内主流 ROM 会清理后台、限制自启动与传感器使用，需要用户手动加入白名单。 必须有保活引导与"被杀检测"，不能假设进程常驻。
相机独占与并发 相机通常被单一应用占用；部分设备不支持前后摄同时采集。 切换镜头需要短暂重连；不做"双摄同时直播"的默认承诺。
应用商店政策 商店普遍禁止隐蔽监视类应用，要求显著披露后台相机使用与合法用途。 首次启动必须做合法用途确认；产品文案不得出现"偷拍""无痕"。
热与功耗 持续采集 + 编码 + 无线传输会显著升温；边充边用会加剧。 必须有温度分级策略与低功耗档位。
数据合规 家庭画面属于个人信息；录音涉及他人声音；跨境传输有额外要求。 默认本地、加密传输、可删除、可审计；云功能单独授权。

2.5 调研结论：六条产品决策

#决策理由
D1同一 App 内置摄像头端与观看端两种角色，而不是两个 App。降低安装门槛；旧设备与新手机都能复用；与 Alfred 的双 App 模型相比少一次下载和一次理解成本。
D2抽象出四种运行模式：值守、黑屏记录、直播、连续记录。不同场景的屏幕策略、功耗策略、退出条件完全不同，混在一个开关里必然互相干扰。
D3局域网直连是一等公民，公网访问是可选增强。开源项目的共同短板是可访问性；商业项目的共同短板是必须上云。两者之间的空档正是机会。
D4录制采用分片容器 + 断录修复。FadCam 已验证：进程被杀、断电、卡满都会发生，普通 MP4 会整段损坏。监控产品的底线是"文件一定能打开"。
D5事件检测放在端侧，告警才联网。既控制流量和功耗，也避免把连续画面送出家门；端侧模型可离线工作。
D6所有"静默"能力都以持续通知与合法用途确认为前提。这是上架与长期运营的前提，也是与"隐蔽摄像头"类应用划清界限的方式。

03产品定位

一句话定位

给家里闲置的 Android 设备一次"值守"的机会：屏幕可以熄灭，画面不会中断；数据默认留在家里，需要时随时能看到。

3.1 差异化

维度同类做法本产品
设备关系摄像头端与观看端分离安装；或只做单机录制。单 App 双角色，配对后自动切换界面重心。
屏幕策略要么常亮预览，要么纯后台无界面。四模式：真熄屏值守、黑屏记录、亮屏直播、连续记录。
数据路径默认上云；或完全不可远程。默认局域网直连；公网走端到端加密中继；云备份显式开启。
可靠性断电即损坏；被杀即静默失联。分片录制 + 自动修复 + 心跳失联告警 + 恢复引导。
与 NVR 的关系二选一。可作为 RTSP/ONVIF 信号源接入 Frigate、Home Assistant，同时保留自有观看端。
合规边界模糊，靠用户自律。写进产品：合法用途确认、持续通知、遮挡与暂停能力。

3.2 不做什么

以下边界用于避免评审时反复拉扯，也用于指导文案与商店描述：

  • 不提供无通知、无指示的隐蔽拍摄；不提供绕过系统快门音的能力。
  • 不承诺"重启后自动开始拍摄"（平台不允许），只承诺重启后提醒与一键恢复。
  • 不把连续录像默认上传到任何第三方服务器。
  • 不做陌生人脸识别、身份库比对等高风险能力；人形检测只用于事件分类。
  • 不在首发版本做 iOS、Web 观看端与硬件配件（列为 P2）。

04用户与角色

4.1 目标用户

画像典型场景最在意的事
独居 / 租房青年 出差或上班期间想看门口与屋内；不想为短期需求买摄像头。 三分钟能用；不要月费；不要上传到别人服务器。
有老人或宠物的家庭 白天无人时观察活动情况；夜间需要低打扰地看一眼。 画面稳定、推送别太吵、能看到回放。
育儿家庭 婴儿房、临时看护；希望屏幕不刺眼、夜里不发光。 黑屏/低亮、双向语音、低延迟。
技术型用户 已有 Frigate / Home Assistant / NAS，想把旧手机当一路信号源。 RTSP/ONVIF、可配置、无广告、可自托管。
私密记录用户 会议、采访、课堂等需要屏幕不亮的记录场景（QuietCam 场景）。 黑屏、点击即拍、文件私密。

4.2 角色定义

角色定义典型设备

Member（家庭成员）被邀请加入的家庭成员，可观看实时、回看事件、接收告警，不能修改设备与安全设置。家人手机、平板
Guest（临时访客）限时查看者，仅在授权时段内可看实时画面，看不到历史与设置。临时照看者、保姆、邻居
Camera 设备采集端设备本身，不是"人"。它的行为受 Owner 配置约束，并在通知中公开自己的采集状态。旧手机、旧平板

05产品模型与范围

5.1 设备角色与运行模式

设备角色回答"它是什么"，运行模式回答"它此刻在做什么"。同一台设备更换角色不需要重装，但同一时刻只能处于一种运行模式。

模式屏幕表现采集行为适用场景退出条件
值守模式
P0		 屏幕关闭（真熄屏） 持续低帧率分析；事件触发时录制；支持远程实时查看。 长期放置的居家监控、出门期间看家。 用户手动停止、电量过低、温度过高、权限被撤回。
黑屏记录
P0		 屏幕点亮但显示纯黑 / 壁纸 / 自定义图 无预览；单击拍照；可录制视频；不参与远程值守。 QuietCam 式私密记录；临时放置但不希望屏幕发光。 长按退出、三指快捷退出、切回值守。
直播模式
P1		 可亮屏显示地址与状态 局域网 MJPEG / RTSP，供浏览器或 NVR 拉流。 接入 Frigate、Home Assistant、VLC、OBS。 手动停止、网络断开超时。
连续记录
P1		 屏幕可关闭 持续分段录制，不依赖事件触发。 需要完整证据链的场景（装修、纠纷、长时间看护）。 手动停止、存储配额耗尽、温度过高。

中断用户看到什么产品做什么

P0

FR-01 首次启动与合法用途确认

目的：在用户拿起设备的第一分钟，就让"这台设备将开始采集"这件事被明确告知，并留下可追溯的确认记录。

触发首次安装后打开应用；或隐私政策/确认条款版本升级后首次打开。
处理规则
  • 用三屏说明产品定位、数据去向、禁止场景，不使用恐吓式文案。
  • 必须主动勾选"我确认仅在本人拥有或已获授权的场所使用本产品"，并点击"同意并继续"。
  • 不强制注册账号；允许跳过账号直接进入本地配对。
  • 记录确认版本、时间、设备型号，仅保存在本机。
结果与状态确认后进入角色选择页；未确认时其余功能不可用，但可查看隐私说明与卸载指引。
异常无网络也可完成确认；拒绝确认则停留在说明页，提供"仅浏览说明"入口。
P0

FR-02 设备角色选择与配对

目的：把"两台设备建立信任关系"压缩成一次扫码，且不依赖账号体系。

触发完成 FR-01 后进入角色选择；或在设备列表点击"添加摄像头"。
处理规则
  • 角色分为"作为摄像头""作为观看端""两者都要"，可随时在设置中更改。
  • 摄像头端生成二维码，内容包含设备标识、临时配对令牌、公钥指纹；同时显示 6 位数字码作为兜底。
  • 配对码有效期 5 分钟，一次性使用；每次刷新生成新码。
  • 同一局域网内，观看端可自动发现处于配对状态的设备并提示"发现附近设备"。
  • 配对时交换设备公钥，建立会话密钥；后续通信默认加密。
结果与状态配对成功后设备出现在观看端列表，状态为"在线·待机"；摄像头端显示"已连接 1 台观看设备"；配对记录写入本机审计。
异常
  • 二维码过期：提示刷新，不要求重新进入流程。
  • 设备已被其他 Owner 配对：提示先解除原配对，需原 Owner 确认。
  • 不在同一网络：提示切换局域网或改用"远程配对"（P1）。
  • 扫码失败：允许手输 6 位码；连续 3 次失败后冷却 60 秒。
P0

FR-03 设备管理

目的：让用户一眼看出"哪台设备在哪、现在是什么状态"，而不是只看到一个 IP 地址。

触发进入观看端首页；或摄像头端被添加/移除时。
处理规则
  • 设备卡片显示：自定义名称、房间标签、缩略图或占位图、在线状态、当前模式、电量、信号、最近事件时间。
  • 支持重命名、更换房间、调整排序、更换封面图。
  • 卡片提示优先级从高到低：告警中（叠加标识）> 离线 > 低电 > 过热 > 存储告警 > 值守中 > 待机。
  • 移除设备需 Owner 二次确认，并说明"将删除本机保存的该设备事件索引"。
  • 摄像头端被移除后立即停止采集，屏幕显示"已被所有者移除"。
结果与状态列表实时刷新，状态变化不需要下拉刷新；离线设备保留最近一张缩略图并标注时间。
异常设备离线超过 24 小时，卡片显示"长期离线"，并提供排查入口；设备数量超过当前授权上限时，仅允许查看已有设备，新增时提示上限。
P0

FR-04 值守模式与屏幕策略

目的：这是产品的核心能力：屏幕熄灭、采集继续、状态可确认、随时可停止。

触发摄像头端用户在可见界面上点击"开始值守"；或观看端（Owner）发送值守请求，摄像头端收到提醒后由现场用户确认启动。
处理规则
  • 启动位置：必须由摄像头端的前台界面确认发起。观看端的请求只产生提醒，不直接启动采集——既符合 Android 对 camera 前台服务的限制，也避免设备在无人知晓时开始拍摄。
  • 屏幕策略：提供"立即熄屏""30 秒后熄屏""保持亮屏"三档。选择熄屏后，屏幕关闭但采集与检测继续。
  • 检测策略：默认开启运动检测，帧率档位分为省电、均衡、流畅；省电档以低帧率分析、事件时提升画质。
  • 状态公开：启动后必须显示持续通知，内容包含设备名、当前模式、已运行时长、停止按钮。
  • 停止方式：通知内停止、应用内停止、观看端远程停止（Owner，局域网内 P0 可用）、低电/过热自动停止。
结果与状态设备状态变为"值守中"；通知常驻；观看端可打开实时画面；本机缓存开始按事件写入。
异常
  • 相机被占用：启动失败并提示占用应用，提供重试。
  • 通知权限未授予：阻止启动，说明"没有持续通知就无法合法采集"。
  • 电池优化未关闭：启动成功但提示"可能被系统中断"，提供一键跳转设置。
  • 屏幕被用户点亮：值守不中断，应用回到锁屏或显示极简状态页。
P0

FR-05 黑屏记录模式

目的：承接 QuietCam 验证过的私密记录体验：屏幕不发光，但相机随时可用。

触发摄像头端切换到"黑屏记录"模式；或从快捷方式/桌面小组件直接进入。
处理规则
  • 屏幕背景可为纯黑、系统壁纸、用户自定义图片三选一；默认纯黑，亮度自动降到最低可读水平。
  • 不显示取景预览；单击屏幕任意位置拍照，拍照后有轻微触觉反馈（可在设置中关闭）。
  • 长按 1.5 秒隐藏所有控件；三指点击三次作为退出快捷手势，避免"进去出不来"。
  • 双击切换前/后镜头；音量下键可配置为快门或录像开关。
  • 视频录制可选 1080p/4K（依设备能力）；文件进入应用私有图库，不出现在系统相册。
结果与状态拍摄文件按时间命名并记录镜头、分辨率、时长；私有图库入口需要 PIN 或生物识别。
异常
  • 机型受系统快门音策略约束：首次进入该模式时明确提示"本机可能无法完全静音"。
  • 屏幕被锁定：采集停止，返回后提示"锁屏会中断记录"。
  • 误触：提供"最近删除"与 30 秒撤销。
P0

FR-06 镜头与画质

目的：用旧设备的硬件差异做适配，而不是假设所有设备都有同样的摄像头。

触发首次进入摄像头端设置；或观看端打开画面设置。
处理规则
  • 自动枚举可用镜头：后置主摄、前置、超广角、长焦（受设备能力限制）。
  • 分辨率档位：720p / 1080p / 2K / 4K，按设备与编码器能力动态置灰。
  • 帧率：15 / 30 fps；值守省电档默认 15fps 分析、事件时提升。
  • 编码：优先 HEVC（省流量），不支持则回退 H.264。
  • 画面：旋转、镜像、时间戳水印、夜间增强开关。
  • 切换镜头会短暂中断画面（约 1 秒），界面需明确提示而不是静默黑屏。
结果与状态设置立即生效并持久化；观看端与摄像头端显示一致的当前配置。
异常不支持的分辨率不可选并说明原因；切换失败回退到上一档；高分辨率导致过热时自动降档并通知。
P0

FR-07 事件检测

目的：把"一直录"变成"有事才记"，这是功耗、存储与通知体验的共同前提。

触发值守或连续记录模式运行中，检测器持续分析画面与声音。
处理规则
  • 运动检测：基于低分辨率帧差与区域权重；灵敏度 1–5；支持划定检测区域（网格勾选）。
  • 声音检测：基于环境音量阈值与持续时间，阈值可调；麦克风权限单独申请。
  • 人形检测：P1，端侧模型输出"有人/无人"与置信度，仅用于分类与降噪，不做身份识别。
  • 预录缓冲：始终保留最近 5 秒环形缓冲，事件触发时从事件前 5 秒开始写入。
  • 合并规则：同一事件源 60 秒内的连续触发合并为一条事件，避免刷屏。
  • 时段计划：仅在设定时段内检测；时段外可继续录制但不推送。
结果与状态生成事件条目（类型、时间、置信度、缩略图），触发片段录制与推送；事件状态从"检测中"进入"已录制"。
异常光线突变、镜头被遮挡、宠物走动造成的误报，通过灵敏度、区域与合并窗口控制；连续误报超过阈值时提示用户调整，而不是让用户关掉功能。
P0

FR-08 实时观看

目的：让用户在两秒内确认"家里现在是什么样"。

触发观看端点击设备卡片；或点击告警通知中的"查看实时"。
处理规则
  • 连接顺序：局域网直连 → 已配对的中继 → 提示网络不可达；每一步给出可读的状态文案。
  • 画面支持：全屏、横屏、截图、静音、画质切换（流畅/标清/高清）、保存当前画面到相册。
  • 实时画面不默认录制到观看端；如需保存证据，使用"录制本段"按钮并明确提示。
  • 观看端切到后台超过 30 秒后暂停拉流，回到前台自动恢复。
  • 多人同时观看时，摄像头端保持单一编码，由服务层做分发（并发上限 [TBD]）。
结果与状态画面显示当前时间、设备名、网络路径（局域网/中继）、码率与延迟指示。
异常
  • 连接超时：先展示最近一张快照与"最后在线时间"，再提供重试。
  • 摄像头端正处于黑屏记录模式：实时观看不可用，提示切换模式。
  • 带宽不足：自动降至子码流，并允许手动锁定清晰度。

FR-09 告警与通知

目的：在正确的时间把正确的信息推给正确的人，并且不制造通知疲劳。

触发事件生成、设备状态异常（离线/低电/过热/被杀/存储满）、值守开始或停止。
处理规则
  • 告警分三级：紧急（人形/连续运动）、普通（单次运动/声音）、提示（设备状态）。
  • 通知内容包含设备名、事件类型、时间、缩略图（可在设置中关闭），点击直达事件详情。
  • 同一设备同一类型 60 秒内只推送一次摘要；免打扰时段只记录不推送。
  • Member 可自行选择接收级别；Guest 不接收。
  • 设备离线期间的事件在本地排队，恢复连接后推送一条"离线期间共 N 条事件"摘要，不逐条补推。
结果与状态通知状态记录为已发送/已送达/已点击；事件详情中可见推送历史。
异常推送通道不可用（无 FCM 或用户禁用通知）：降级为应用内消息中心；投递失败重试 3 次后标记失败。

FR-10 本地录制与存储

目的：保证"事件发生时一定留下了能打开的文件"，并让用户知道空间去哪了。

触发事件触发录制；或连续记录模式启动。
处理规则
  • 采用分片写入的 MP4 容器：录制过程中持续落盘，停止时收敛为通用 MP4；进程被杀或断电后，下次启动自动扫描并修复。
  • 单段时长默认 30 秒（连续记录）/ 事件前后各 5 秒与 10 秒（事件录制）。
  • 存储配额：用户可设上限，默认不超过设备可用空间的 50%；低于 15% 剩余空间时触发清理。
  • 循环覆盖顺序：已过期且未锁定 → 最旧 → 最近。锁定片段、最近 24 小时事件永不自动删除。
  • 文件默认存放于应用私有目录；导出到系统相册需用户手动触发。
  • 可选本地加密（P1），密钥由 Android Keystore 保护，卸载后不可恢复。
结果与状态存储页显示已用空间、片段数量、最早与最晚时间；每个片段标注"完整/已修复/损坏"。
异常写入失败降级到内部存储并提示；SD 卡被移除时暂停录制并告警；修复失败保留原始文件并标注，不自动删除。

FR-11 事件回看

触发观看端进入"事件"页；或从通知、设备详情进入。

FR-13 电源、保活与故障恢复

目的：承认"旧设备会没电、会发热、会被系统杀掉"，并把每一次失败都变成一次可解释的提示。

触发值守中持续监测电量、温度、网络、进程存活与相机占用。
处理规则
  • 电量：低于 20% 进入省电降级（降低分析帧率、关闭语音与实时推流）；低于 10% 停止值守并推送。充电中恢复标准档。
  • 温度：超过 45°C 降帧与降分辨率；超过 50°C 暂停采集并建议改善通风或降低画质；恢复后自动回到原配置。
  • 心跳：摄像头端每 30 秒上报一次；观看端超过 90 秒未收到则标记"疑似中断"，并给出排查步骤。
  • 保活引导：分步引导关闭电池优化、允许自启动、锁定后台；不同厂商给出对应入口名称。
  • 重启：不尝试自动启动相机；发送"设备已重启"通知，用户打开应用后一键恢复上一次模式与设置。
  • 网络：断网时本地录制继续；恢复后补传事件索引与缩略图。
结果与状态健康记录中保留最近 7 天的状态事件；设备卡片上直接展示当前最严重的一条。
异常降级后仍过热：暂停并明确告知"设备需要休息"；连续 3 次被系统杀死：建议改用常电供电与降低画质。

FR-14 隐私、安全与遮挡

目的：让用户相信"只有我能看"，并让这种相信有可见证据。

触发配对完成、开启任何远程能力、成员访问、导出或删除数据时。
处理规则
  • 配对时交换密钥；传输默认 TLS；公网中继传输端到端加密，中继节点无法解密画面。
  • 私有图库、设置页、成员管理需 PIN 或生物识别（可开关）。
  • 隐私遮罩：用户可在画面中划定区域，录制与直播时该区域被涂黑/模糊。
  • 一键暂停：观看端可请求暂停，摄像头端收到后 5 秒内停止采集并显示"已被远程暂停"。
  • "谁在看"：摄像头端始终显示当前观看人数；观看端显示"画面仅你与 N 位成员可见"。
  • 云备份默认关闭；开启需二次确认并单独说明数据去向、保留期与删除方式。
结果与状态安全设置变更记录在审计日志；远程暂停后设备状态变为"已暂停"，不会自动恢复。
异常密钥轮换失败时阻止公网访问，仅保留局域网；设备丢失时 Owner 可远程解除配对并清空索引。

FR-18 跨端交互规范

目的：统一摄像头端与观看端的手势、状态语言与反馈方式，避免同一产品出现两套操作逻辑。

触发所有界面与交互设计。
处理规则
  • 同一动作在不同端保持同一含义：单击=查看/拍照，长按=隐藏或更多，双击=切换镜头。
  • 所有破坏性操作（停止值守、删除片段、移除设备、解除配对）必须二次确认并说明后果。
  • 状态色固定：绿色=正常值守，琥珀=需要注意，红色=中断/告警，灰色=离线。不得用颜色单独传达信息。
  • 触控目标不小于 44×44 dp；支持系统字体放大至 200%；深色模式为默认。
  • 所有空态给出下一步动作，而不是空白页。
结果与状态设计评审以本规范为准；新增界面需在评审中标注所使用的既有交互语言。
异常小屏设备（< 360dp）允许折叠次要信息，但不得隐藏状态与停止入口。

环节实现策略理由
相机接入优先采用 CameraX 的统一用例模型；对特殊机型回退 Camera2 能力探测。旧设备碎片化严重，需要一层能力探测与降级。

编码硬件编码优先；码率随画质档位与网络状况调整；支持 HEVC 回退 H.264。软件编码在旧设备上会迅速升温降频。
文件格式分片写入的 MP4，边录边写；停止时收敛；异常后扫描修复。FadCam 已验证该方案能在进程被杀后保住大部分内容。
检测低分辨率帧差为主，端侧轻量模型为辅；仅在 P1 引入人形分类。控制功耗；旧设备算力有限；避免误报导致通知疲劳。
音视频同步以采集时间戳对齐；对讲与录像使用不同通道，避免互相抢占。双向语音与录制并发时最容易出现音画不同步。

10.3 连接与安全

能力策略说明
局域网发现mDNS / NSD 广播服务；配对后记住设备指纹。减少用户输入 IP 的成本。
局域网传输HTTP 流 + 令牌认证；默认仅局域网可访问。兼容浏览器与 NVR；令牌可重置。
公网访问WebRTC 打洞优先，失败走 TURN 中继；媒体端到端加密。中继只转发密文，降低"云能看到画面"的顾虑。
配对安全二维码携带一次性令牌 + 公钥指纹；配对完成即失效。防止截图重放与中间人。
本地数据应用私有目录；可选加密；卸载即删除。避免被其他应用或相册扫描读取。
远程控制所有远程操作走已认证通道并记录审计。暂停、停止、移除设备必须可追溯。

10.4 保活与功耗

问题策略
系统回收前台服务 + 持续通知；申请电池优化豁免；提供厂商自启动白名单引导。
屏幕关闭后休眠使用部分唤醒锁维持 CPU 与采集；屏幕本身不保持唤醒。
功耗动态帧率、按需编码、事件时提升画质、无事件时降低分析频率；充电时允许高性能档。
发热温度分级降载；避免长时间 4K；提示移除保护壳与避免阳光直射。
重启恢复不自动启动相机（平台限制）；改为通知 + 一键恢复上次模式。

10.6 技术风险

风险等级影响与应对
厂商 ROM 杀后台高直接导致值守中断。应对：心跳检测、白名单引导、降低功耗、提供"被杀原因"解释，而不是静默失败。
相机被其他应用占用中值守启动失败或中断。应对：占用检测、重试、提示关闭占用应用。
持续采集发热高旧设备散热差，夏天更明显。应对：温度分级、默认 1080p/15fps、避免 4K 长时间运行。
文件损坏中使用分片容器与修复机制；损坏文件标注而非删除。
公网打洞失败中中继兜底；中继成本与带宽需要商业模型支撑 [TBD]。
商店政策审核高后台相机与"黑屏"能力容易被误判为隐蔽监视。应对：显著披露、合法用途确认、商店描述避免敏感词、保留审核说明材料。
快门音地区差异中能力清单标注限制；不将其作为卖点。
旧设备性能基线过低中设置最低支持版本与"仅黑屏模式"降级路径。

12UI 升级方案

12.1 设计原则

暗色优先

监控多发生在夜间与弱光环境，默认深色可减少屏幕对环境的干扰，也贴合"设备应融入环境"的产品气质。

一屏一任务

观看端首页只回答"我的设备现在怎么样"；实时页只回答"现在发生了什么"；事件页只回答"之前发生了什么"。

状态永远可见

任何界面都能看到设备当前是否在采集、是否在线、电量是否足够。不使用隐藏式开关表达采集状态。

破坏性操作可撤回

删除、停止、移除、解除配对都提供确认与短时撤销，避免误触造成证据丢失。

14开放问题

#问题为什么必须在评审中拍板
Q1正式产品名与商标是否可用？"静哨 QuietSentry"为工作名。影响商店上架、域名、文案与图标设计。
Q2是否需要账号体系？纯本地配对可离线，但成员共享与公网访问需要身份。决定架构复杂度、隐私承诺与运营成本。
Q3公网访问由自建中继承担，还是引导用户使用 Tailscale 等自组网？中继带宽是持续成本；自组网会提高用户门槛。
Q4免费与付费的边界：设备数、云备份、AI 分类，哪一项进入订阅？直接影响商业模型与"本地优先"承诺的可信度。
Q5最低支持版本定为 Android 9 还是 Android 10？影响覆盖设备范围与相机能力基线。
Q6是否在首发版本提供 RTSP/ONVIF，还是留到 P1？技术型用户是关键口碑来源，但会拉长开发周期。
Q7并发观看上限与设备数上限分别是多少？影响编码策略、带宽估算与服务端设计。
Q8是否需要"仅充电时值守"作为默认策略？旧设备电池健康差异大，默认策略会影响可用性感知。
Q9黑屏记录模式是否与主产品同包发布？商店审核对"黑屏相机"敏感，可能需要独立产品线或更强的披露设计。
